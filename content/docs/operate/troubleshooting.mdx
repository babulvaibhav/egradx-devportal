## Sign-in and sessions

### Every request is 401, even signed in (Java)

You declared your own `SecurityFilterChain`, and it replaced the SDK's without adding its filter, so no request is ever authenticated. Add `egradxAuthenticationFilter` before `UsernamePasswordAuthenticationFilter`, and the SDK's entry point. See [identity](/docs/guides/identity#in-oim).

### Sessions end at random, or 401 loops after a deploy

Two instances made different keys. That happens when they started together on an empty keys folder, or used different folders. Tokens signed with one key are refused by instances holding the other. Give every instance the same folder and passphrase, start one first, then restart the rest. People sign in once more. See [keys](/docs/guides/keys#rules).

### `SESSION_EXPIRED` right after signing in, on another instance

The issuer differs between instances, or one of them can't read the keys (a different passphrase). Every instance needs the same `issuer` and keys.

### `ORG_SELECTION_REQUIRED` at sign-in

The person belongs to several organizations. Sign in again with `organizationId` set to one from `details.organizations`. The generated login form does this.

### The Google or Zoho button doesn't appear

The provider was left out at startup, which logs what it needs: its client id and secret, `oidc.callback-base-url`, and `links.base-url`. `GET /egradx/auth/sign-in-options` lists the providers on offer. See [sign-in methods](/docs/guides/sign-in-methods#configuration).

### The provider says `redirect_uri_mismatch`

The redirect URI registered with the provider must be exactly `{callback-base-url}/egradx/auth/oidc/{id}/callback`: same scheme, host, port and path prefix, no trailing slash. Behind the Next.js backend-for-frontend, `callback-base-url` is the BFF's public prefix.

### `/auth/callback?error=OIDC_FAILED`

The code exchange or the ID token check failed: a wrong client secret, a custom provider's wrong `issuer`, the API unable to reach the provider, or a clock more than 60 seconds off. The API's log says which. `OIDC_STATE_INVALID` means the round trip took over 10 minutes or was replayed.

### `EMAIL_CODE_UNAVAILABLE`, or no "email me a code"

Nothing delivers account messages, or `email-code.enabled` is false. Email must work ([configure SMTP](/docs/recipes/configure-smtp)). `egradx-sdk` includes the sender in every language (`egradx-notification-auth`); an application wiring the packages one by one adds it.

### The platform administrator gets 403 on my endpoints

That is by design: the platform administrator holds every SDK authority and none of yours. To work inside an organization they need a membership there.

### A permission granted doesn't apply yet

On other instances, a role's authorities are cached for up to 60 seconds. If it never applies: is the authority on the role the person holds **in the organization their session is in**?

## Errors

### My endpoint answers 500 for a `NotFoundException` (Java)

`egradx-sdk` answers your endpoints in the envelope through its fallback advice, `EgradxApplicationExceptionHandler` ([errors](/docs/guides/errors#wiring-the-envelope-in)). If you still get Spring Boot's format:

- Your `egradx-sdk` 1.0.0 predates the fallback (it ships with the next republish; see [what's new](/docs/whats-new)): keep the generated `ApiExceptionHandler`, or fetch the package again.
- `egradx.errors.fallback.enabled` is `false`.

If refusals come back as 500s, your own advice has a catch-all `@ExceptionHandler(Exception.class)`: it answers before the fallback and catches `AccessDeniedException` too. Handle that exception as well, as the generated advice does, or handle only your own exceptions.

### Node: errors come back as HTML

`app.use(...egradxErrors())` must come **after** every route.

## Migrations

### "…was changed after it was applied"

An applied migration file was edited. Restore it, and put the change in a new migration.

### `relation "egradx_organization" does not exist`

Your migrations ran before the SDK's sign-in tables. In Node and Python, pass yours to `migrateEgradx` / `migrate_egradx` as the application step. See [migrations order](/docs/recipes/migrations-order).

### The Java build seems to ignore my changes

The IDE wrote `target/classes` and Maven skipped compiling. Run `mvn clean …`.

## Email and notifications

### Nothing arrives

Look at the delivery log: `GET /egradx/notifications/admin/deliveries`. `lastError` says why. Common causes are a wrong host or port, TLS on the wrong port, or a missing `from`.

### `CHANNEL_UNAVAILABLE` when sending

The channel isn't set up for that organization. `GET /egradx/notifications/admin/channels` gives the `unavailableReason`.

### Saving SMTP or Slack credentials fails (Node, Python)

No secrets passphrase. Set `EGRADX_NOTIFICATION_SECRETS_PASSPHRASE`, or pass `secrets.passphrase` / `secrets_passphrase`.

### No password-reset or invitation emails

`links.base-url` isn't set. Invitations then fail with `INVITATION_DELIVERY_UNAVAILABLE`; reset requests still answer 202, with no email.

### The bell doesn't update live

A proxy is buffering `/egradx/notifications/stream`. Turn buffering off for it. With several instances, a notice is live only on the instance that published it.

### The application doesn't start: a template uses an undeclared variable

Add the variable to the type's `requires` / `optional`, or fix the template. The message names both.

## Files

### Uploads fail with a bare 413

A proxy in front of the API refused the body before the API saw it: the answer is not the error envelope, so the client reports `HTTP_413` rather than `FILE_TOO_LARGE`. nginx allows 1 MB by default. Raise its limit above `egradx.files.max-size` (`client_max_body_size 30m;` for the 25 MB default), and any ingress's or load balancer's too. The API's own refusal is `FILE_TOO_LARGE` in the envelope.

### With Next.js, uploads over 10 MB arrive broken

`proxy.ts`'s matcher includes the backend-for-frontend's path, so the proxy holds the body and cuts it at `experimental.proxyClientMaxBodySize` (10 MB). Exclude the path, as the generated matcher does (`/((?!bff/|_next/|favicon.ico).*)`), or raise that setting above `max-size`.

### Images and photos don't show

- **A plain `<img src>` with tokens in the browser** (Vite): the browser sends no bearer token, so the API answers 401. Use `useFileObjectUrl`, `useProfilePhoto` or `client.files.displayUrl`, which download with the session.
- **They download, but stay blank:** the Content-Security-Policy refuses the `blob:` URL. Add `blob:` to `img-src` (and to `frame-src` for PDFs shown in a frame).
- **Another organization's photo** answers 404: photos are readable only in the organization they were uploaded in.

### A download fails from a script with pre-signed downloads on

The API answers 302 to the bucket, and the browser's `fetch()` of the bucket is cross-origin. Allow your frontend's origin on the bucket with a CORS rule: `GET` (and `HEAD`), the `Range` header, and `Content-Disposition`, `Content-Length` and `ETag` exposed. `<img>` and links don't need it. The bucket's address must also be one the browser can reach.

### `FILE_STORAGE_UNAVAILABLE`

The backend can't be reached: on local disk, the folder isn't writable by the application (in a container, the volume's owner); on S3, a wrong endpoint, bucket, region or keys, a bucket that doesn't exist, or `path-style` off for a store that needs it. The application's log has the cause. Java with `backend: s3` doesn't start at all without `software.amazon.awssdk:s3` on the classpath.

### `ACCESS_DENIED` on a record's files

The record's access policy said `DENY`, or `DEFAULT` and the caller lacks `egradx.file.read`, `.write` or `.delete`. Only Admin roles hold those by default. Check the policy for that `attachedType`, and that it finds the record in the caller's organization.

## Events

### Events are never handled

- Node and Python: `events.start()` was never called, or `migrateEvents` / `migrate_events` didn't run.
- In-process with two different services on one database: one relays events the other should handle. Use a broker.
- A handler keeps failing: see [dead letters](/docs/recipes/dead-letters).

### An event arrives a couple of seconds late

It was published with an explicit transaction (`{ tx }` / `connection=`). The relay picks it up on its next poll, up to 2 seconds later.

## Running locally

### Python on Windows: `ProactorEventLoop` errors from psycopg

psycopg's async mode needs the selector event loop. The generated `__main__.py` and `tests/conftest.py` set it.

### Python in a container: connection refused

uvicorn listened on 127.0.0.1. Set `HOST=0.0.0.0`, as the generated Dockerfile does.

### Garbled characters in a Windows console

The console uses cp1252. Run `chcp 65001`, or set `PYTHONUTF8=1` for Python.

## Still stuck

Every error body has a `requestId`. Search the logs for it: the failure is logged with its stack trace, under that id.
