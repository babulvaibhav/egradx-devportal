Called inside the change's transaction, the message is queued with it. If the change rolls back, nothing is sent. Sending happens later, on the dispatcher, so a slow mail server never slows the request.

`send` checks everything before it queues: the channel is set up, the template renders with these variables, the addresses are valid. If not, it refuses with a 400: `CHANNEL_UNAVAILABLE`, `TEMPLATE_INVALID` or `RECIPIENTS_UNREACHABLE`.

## 3. Point it at a mail server

Locally, the generated compose file runs Mailpit; open `http://localhost:8025` to read what was sent. For production, see [configure SMTP](/docs/recipes/configure-smtp).

A user receives it at their **verified** email address, or the one they sign in with. If the type is declared `userCanOptOut()` and they turned it off, they don't receive it.

## When the email must never fail the change

An email queued in the transaction is atomic with it, which is usually what you want. If you'd rather lose the email than fail the change, send it after the commit and catch everything, as OIM's low-stock alert does: see [notifications](/docs/guides/notifications#messages-that-must-not-break-the-change).
