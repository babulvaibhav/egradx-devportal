---
title: Run the SDK's migrations before your own
description: The order the SDK's tables and yours are created in, so your tables can reference organizations and users — in each language.
---

Your tables reference the SDK's (`organization_id … REFERENCES egradx_organization (id)`). So the order is:

1. the SDK's **sign-in** tables;
2. **your** migrations;
3. the **audit** trail's, then **notifications'**, then **events'** (if you use them).

Each library keeps its own history table (`egradx_auth_schema_history`…), so its versions never collide with your `V1`, `V2`.

<Languages>
<Tab value="Java">

Nothing to write. At start-up each library migrates with its own Flyway instance, in this order, and Spring Boot's Flyway runs yours from `src/main/resources/db/migration` in between:

<RepoSnippet file="apps/egradx-devportal/examples/java/backend/src/main/resources/db/migration/V1__notes.sql" region="migration" title="backend/src/main/resources/db/migration/V1__notes.sql" />

On a new database your Flyway finds tables already there and starts from a baseline of 0, so your `V1` still runs. If you set `spring.flyway.baseline-on-migrate` yourself, your setting wins.

</Tab>
<Tab value="Node">

Migrate before creating the SDK. `migrateEgradx` takes your migrations as a step in the middle:

<RepoSnippet file="apps/egradx-devportal/examples/node/backend/src/app.ts" region="main" title="backend/src/app.ts" />

`migrate({ database, location, table })` runs your SQL files (`V1__notes.sql`, `V2__…`) with the SDK's runner. It uses Flyway's history format and checksums, and an advisory lock so instances don't race. Prisma only maps your tables: don't use `prisma migrate`.

</Tab>
<Tab value="Python">

Migrate before starting the SDK, with your migrations in the middle:

<RepoSnippet file="apps/egradx-devportal/examples/python/backend/src/notes/app.py" region="main" title="backend/src/notes/app.py" />

`migrate_async(url, folder, table)` runs your SQL files with the SDK's runner. It uses Flyway's history format and checksums, and an advisory lock.

</Tab>
</Languages>

## When it goes wrong

| Message | Meaning |
|---|---|
| "…was changed after it was applied" | an applied migration file was edited. Put the file back, and add a new migration instead. |
| `relation "egradx_organization" does not exist` | your migrations ran before the SDK's sign-in tables. Fix the order above. |
| Java: `Found non-empty schema(s) … but no schema history table` | you set `baseline-on-migrate: false`. Remove it, or baseline once. |

## Sharing a database across languages

All three ship the same SQL, so Java, Node and Python services can share one database. Give your own history table the same name in each (Java uses `flyway_schema_history`), so whichever service starts first applies your migrations once.
