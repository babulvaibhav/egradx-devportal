## 1. A text column

```sql title="V2__partner_secret.sql"
ALTER TABLE notes_partner ADD COLUMN api_key_sealed TEXT;
```

A sealed value is one string: `v1:<salt>:<wrapped key>:<ciphertext>`. It is AES-256-GCM, with a key derived from your passphrase (PBKDF2-SHA256, 210 000 rounds).

## 3. Keep the passphrase elsewhere

- Read it from the environment or a secret store, never from the code or the database.
- Use a passphrase of its own, not the keys passphrase. Then a leak of one doesn't open the other.
- **Changing it** means opening every value with the old passphrase and sealing it again, in a migration of your own.

## Rules

- **Never return the value.** Answer "set" or "not set", as the SDK does for channel secrets; accept a new value to replace it.
- **Never log it**, and never put it in an audit state. The auditor redacts keys named like `secret`, `token`, `password` or `apiKey`; with any other name, add the key to `redaction.keys`.
- **Seal only what you must read back.** For a password people sign in with, use a hash; the SDK's sign-in already does that.

## Across languages

The format is pinned by test vectors in the SDK's contracts: a value sealed in Java opens in Node and Python, and the other way round.
