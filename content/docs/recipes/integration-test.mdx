Every project [the Initializr](/start) generates with **Tests** has this test, and it passes as generated.

## 1. A database for tests

The generated compose file creates `<app>_test` beside `<app>`. The application migrates it on start, the SDK's tables and yours, as in production. Point elsewhere with `TEST_DB_URL` (Java) or `TEST_DATABASE_URL` (Node, Python).

## What makes it work

- **Signing in for real:** `POST /egradx/auth/login` as the demo administrator the application seeds at start-up, then `Authorization: Bearer …` on every call. Use real tokens, not mocks: the SDK checks each request against the database.
- **A keys folder per run:** a temporary directory, so tests never touch the development keys.
- **Its own SMTP server,** so email can be checked (see [check an email](/docs/recipes/assert-audit-and-email)).
- **A refusal is a result too:** without a token it's 401 `NOT_AUTHENTICATED`; without the authority, 403 `ACCESS_DENIED`. Test both.

## A second person

To test the 403, create someone with a role that lacks the authority. Provision an organization in the test with its own administrator, or invite and accept through the API. Different organizations also prove that one can't see the other's data (404).

## Not yet: a test kit

A kit with a signed-in client, captured mail and events, and audit assertions is planned. Until then, copy this pattern.
