OIM is a real application of the kind teams build on the SDK: products, warehouses, stock, customers and orders, for many organizations at once. It exists to show what building on the SDK looks like, and every guide ends with how OIM does it.

| Part | Built on | Notes |
|---|---|---|
| `backend/` | Java: Spring Boot and the Java SDK | the reference |
| `backend-node/` | Node: Express, Prisma and the Node SDK | the same endpoints and answers |
| `backend-python/` | Python: FastAPI, SQLAlchemy and the Python SDK | the same endpoints and answers |
| `frontend/` | Vite, React Router and `@babulvaibhav/egradx-react` | its own screens, on the hooks |
| `frontend-next/` | Next.js and `@babulvaibhav/egradx-next` | the copy-in screens, tokens in HttpOnly cookies |

The backends are interchangeable down to the database. Any of them can migrate and run on a database another one created, and two can serve one database at once. A token, a session or an audit record from one is valid on the others.

## What is the SDK's, and what is OIM's

| The SDK's (OIM has no code for it) | OIM's |
|---|---|
| sign-in, sessions, users, roles, organizations, invitations, password reset, profiles | products, warehouses, inventory, customers, orders, the dashboard |
| the audit trail, its search and export | the audit records of its own changes, and their words on screen |
| the bell, email, Slack, SMS, WhatsApp, templates, preferences, delivery log | what to send, and when (the low-stock alert) |
| request ids, traces, metrics, the error envelope | its own error codes, such as `INSUFFICIENT_INVENTORY` |
| the signing keys, migrations of the SDK's tables | its own tables and migrations |

**OIM has no authentication, user, role or organization code**: no controller, service or DTO. Its screens for all of it call the SDK's endpoints directly. What OIM adds is one listener that gives every new organization a Manager and a Staff role beside the SDK's Admin, and its permission catalog.

## How it is tested

- **Browser tests** (Playwright): twelve tests run against each of the six backend and frontend combinations. They cover sign-in kept across a reload, a notice arriving live in the bell, a refused token renewed unnoticed, sign-out followed in another tab, password reset through Mailpit, the audit screen and its export, channel settings with a test send, verifying an address, organization choice and switch, and a session ended elsewhere.
- **Parity:** a script calls the Java backend and the Node or Python one with the same requests, and compares the answers.
- **Concurrency:** the Java backend's tests reserve stock from 100 threads at once.
