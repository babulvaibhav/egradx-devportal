---
title: Inventory under concurrency
description: How OIM keeps stock exact when orders race — single-statement stock moves, a status compare-and-swap, and a fixed lock order for transfers.
---

Stock is the one thing in OIM that many people change at once. Three small techniques keep it exact, in every backend. None of them is in the SDK; they are what an application on it still has to get right.

## 1. Every stock move is one statement

Reserving stock for an order checks and changes it in **one** `UPDATE`, which the database runs atomically. A read followed by a write would let two orders both see the last 5 units.

`available_quantity >= :quantity` in the `WHERE` is the check. Zero rows updated means there wasn't enough, and the service answers 409 `INSUFFICIENT_INVENTORY`. The organization is in the `WHERE` too: one statement, both rules.

The Java backend's tests run 100 threads, each reserving 1 unit of a product with 10 available. Exactly 10 succeed, and the row ends with 0 available and 10 reserved.

## 3. Transfers lock rows in one order

A transfer debits one warehouse and credits another. Two transfers in opposite directions, A→B and B→A, would each lock one row and wait for the other: a deadlock. Locking the two rows in a fixed order (the lower id first) makes that impossible:

## Where the SDK comes in

Each of these runs in a transaction that the SDK's audit records, notices and events join. A stock move that fails rolls back its audit record and its notice too, and a successful one commits them together.
