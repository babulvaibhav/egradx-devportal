The EGRADX SDK is a set of **libraries that run inside your application**. There is no separate EGRADX server to deploy: your application adds a dependency, points it at its PostgreSQL database, and gets the cross-cutting features every business application needs.

## What it gives an application

| Capability | What you get |
|---|---|
| **Sign-in & identity** | Users, organizations, roles and permissions, invitations, password reset, email change, profiles, sessions, switching organization — with its endpoints and tables |
| **Authorization** | The caller's permissions resolved on every request; one annotation or one middleware to protect an endpoint |
| **Audit trail** | An append-only record of who changed what, written in the same transaction as the change, with filters, history, CSV export and retention |
| **Notifications** | An in-app inbox with a live bell, email, Slack, SMS, WhatsApp and webhooks, templates, people's preferences, bulk sends |
| **Files** | Uploads attached to your records and profile photos, on local disk or any S3-compatible bucket, with permissions, your own access check and streamed downloads |
| **Events** | Business events as CloudEvents, through a transactional outbox, handled once per handler; in-process, RabbitMQ or Kafka by configuration |
| **Observability** | Request ids on every log line, traces, metrics, and log shipping, with the same names in every language |
| **Errors** | One error envelope and one set of codes, across every endpoint and every language |
| **Web** | A browser client, React hooks, a Next.js backend-for-frontend, and copy-in screens |

## Three languages, one behaviour

The SDK exists for **Java** (Spring Boot), **Node** (Express, TypeScript) and **Python** (FastAPI). The three share their database tables, their HTTP API, their error codes and their event format. They are checked against the same language-neutral contracts and the same conformance tests, so a service in one language and a service in another work together, and can even share one database.
