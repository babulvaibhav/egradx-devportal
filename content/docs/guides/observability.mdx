## What it is

When something goes wrong, you need to find everything one request did: its log lines, its error, the audit records and messages it wrote, the events it published, and the trace across services. The SDK ties them together with ids:

| | Where it comes from | Where it shows up |
|---|---|---|
| **Request id** | the caller's `X-Request-ID` (or `X-Trace-Id`), else a new UUID | the `X-Request-ID` response header, every log line, error bodies, audit records, queued messages, published events, handlers' log lines |
| **Trace id** | the W3C trace context, when tracing is on | log lines, error bodies, audit records; spans in Jaeger |

The browser client sends a fresh `X-Request-ID` with every call, and shows it on an error, so a user's report leads straight to the logs.

What the SDK measures, with the same names everywhere (each timer tagged `egradx.outcome`):

| Area | Timers | Counters and gauges |
|---|---|---|
| Sign-in | `egradx.auth.login`, `.refresh`, `.organization.switch`, `.sessions.revoke`, `.password.*`, `.email_change.*`, `.invitation.*`, `.cleanup` | — |
| Audit | — | `egradx.audit.recorded`, `.suppressed`, `.write.failed` (alert on it), `.sink.failed` |
| Notifications | `egradx.notification.send`, `.submit`, `.bulk.submit`, `.bulk.expansion`, `.delivery` | `egradx.notification.delivery.enqueued`, `.delivery.dead` (alert on it), `.delivery.discarded`, `.delivery.backlog` (gauge), `.inbox.published`, `.inbox.connections` (gauge) |
| Events | `egradx.events.publish`, `.send`, `.handle` | — |

In Prometheus they read `egradx_auth_login_seconds_count` and so on (Node leaves out `_seconds`). Your own metrics can use the same helpers: `EgradxMetrics` / `otelMetrics()` / `OtelMetrics()`. Tag names that identify a person or an id are refused, so cardinality stays bounded.

## Log shipping

Every log line can also leave the service as an `egradx.log.record.v1` event — with its level, logger, message, stack trace, service, trace, request, person and organization — over the [events transport](/docs/guides/events). Whatever stores your logs handles that event type.

Best effort, never in the way: logging only queues the line; a background sender ships batches straight over the transport (not through the outbox). A full queue drops lines and counts them. With the in-process transport and no handler for `egradx.log.record.v1` in the same service, lines go nowhere — shipping is for a broker.

| | Java (`egradx.observability.logging.shipping.*`) | Node / Python | Default |
|---|---|---|---|
| On | `enabled` | wire `EgradxLogShipper` | off |
| Lowest level shipped | `minimum-level` | `minimumLevel` / `minimum_level` | INFO |
| Queue, batch, flush | `queue-capacity`, `batch-size`, `flush-interval` | `queueCapacity`, `batchSize`, `flushIntervalMs` / `queue_capacity`, `batch_size`, `flush_interval` | 10 000, 200, 1 s |
| Never shipped | `excluded` (logger prefixes) | `excluded` | the transports' own loggers |

## Health checks

The SDK has none of its own yet. Java applications use Actuator's `/actuator/health` (turn off the mail health check: an SMTP outage should only delay email). In Node and Python, serve your own.

## Guarantees and limits

- **The same ids in every language**: a request that crosses a Java and a Node service is one trace, and its request id follows it into event handlers.
- **Untrusted ids are refused**: an incoming request id must be 1–64 characters of letters, digits, `.`, `_`, `-`; otherwise a new one is made.
- **No metrics for dead events yet**: watch the outbox's `dead_at`, `<queue>.dead` and `.DLT`.

## In OIM

OIM runs Jaeger (`:16686`) and Prometheus (`:9090`) in its compose file; a stock change and the alert emails sent seconds later on the dispatcher are one trace, and the delivery log can be searched by trace id.
