## What it is

Two separate things, never implied by each other:

| | In-app | Everything else |
|---|---|---|
| What | A notice in people's inbox — the bell — pushed live to open pages | A message on a channel: email, Slack, SMS, WhatsApp, a webhook, or one of yours |
| Call | `publishToOrganization`, `publishToUser`, `publishToPlatform` | `messenger.send(EgradxMessageRequest…)` |
| Content | a title, a body, a key and ids for the frontend | a **template** per message type and channel, in each recipient's language |
| Stored | one row per call, read state per person | an outbox: one delivery per address, retried, logged |
| Who | everyone in the organization, one person, or everyone | users (at their **verified** address), raw addresses, or a whole organization |

To tell people in the app *and* by email, make both calls.

## How it works

<Mermaid chart={`sequenceDiagram
  participant S as Your service
  participant D as PostgreSQL
  participant X as SDK dispatcher
  participant P as Mail server / Slack / Twilio
  participant B as Open browsers
  S->>D: your change + in-app notice + queued message (one transaction)
  D-->>S: commit
  S-->>B: the notice, live (after commit)
  X->>D: claim due deliveries (lease)
  X->>P: send
  X->>D: SENT, or retry later (30 s … 32 min), or DEAD`} />

Nothing is sent on your request's thread, and nothing is sent for a change that rolled back. The dispatcher runs inside your application, on every instance at once without double-sending; there is no broker.

## Where messages go

| Channel | Address | Set up by |
|---|---|---|
| `email` | an email address | an organization's own SMTP settings, else ones stored for all organizations, else **your application's mail server** |
| `slack` | a Slack member or channel id | the organization's bot token |
| `sms` | an E.164 number | the organization's Twilio account (or a provider of yours) |
| `whatsapp` | an E.164 number | Meta or Twilio; outside 24 hours only approved templates arrive |
| `webhook` | an `https://` URL | nothing needed; signed with HMAC when a secret is stored |
| yours | anything | a channel of your own (an `EgradxNotificationChannel`) |

Organization administrators set their channels at `/egradx/notifications/admin/channels/*` — or on the [copy-in channels screen](/docs/guides/web#copy-in-screens). Secrets (SMTP passwords, tokens) are encrypted with the secrets passphrase and never returned.

Your application's own mail server, for every organization without settings of its own:

| Java | Node | Python |
|---|---|---|
| `spring.mail.host`, `.port` + `egradx.notification.email.from` | `notifications: { builtInChannels: { email: { transport, from } } }` | `NotificationsOptions(built_in_channels=BuiltInChannels(email=ApplicationEmail(SmtpTransport(host, port), sender=…)))` |

## People and their preferences

- A user receives on a channel only at an address they have **verified** with a code — except email, which falls back to the address they sign in with.
- A type declared `userCanOptOut()` appears on people's settings; sends honour it. Account messages (password reset) can't be opted out of.
- `toOrganizationMembers()` sends to every active member (a bulk send: at most 1000 by default, expanded in the background), `toAddresses(...)` to people who aren't users.

## Messages that must not break the change

A message queued in your transaction is atomic with it — good for "your note is saved". When a message must never be able to fail the change (an alert on several channels, best effort), send it **after** the commit, each channel on its own, catching everything. ## Configuration

| | Java (`egradx.notification.*`) | Node (`notifications: {…}`) | Python (`NotificationsOptions(…)`) | Default |
|---|---|---|---|---|
| Your templates | `templates.locations: classpath:notification-templates/` | `templates: { directories }` | `template_directories` | none |
| Sender, with your mail server | `email.from`, `email.from-name` | `builtInChannels.email.from`, `fromName` | `ApplicationEmail(sender=…, sender_name=…)` | — |
| Secrets passphrase | `secrets.passphrase` (else the keys passphrase) | `secrets: { passphrase }` (else `EGRADX_NOTIFICATION_SECRETS_PASSPHRASE`, `EGRADX_SECURITY_CRYPTO_PASSPHRASE`) | `secrets_passphrase` (same fallbacks) | — |
| This instance delivers | `dispatcher.enabled` | `dispatcher: { enabled }` | `DispatcherSettings(enabled=…)` | true |
| Attempts, backoff | `dispatcher.max-attempts`, `.backoff.*` | `dispatcher: {…}` | `DispatcherSettings`, `EgradxBackoffPolicy` | 8; 30 s doubling to 1 h |
| Bulk send cap | `bulk.max-recipients` | `bulk: { maxRecipients }` | `bulk_max_recipients` | 1000 |
| Keep sent / dead / in-app | `retention.sent`, `.dead`, `.in-app` | `retention: {…}` | `RetentionSettings(…)` | 30 d / 90 d / 365 d |
| The logging channel | `channels.log.enabled` | `builtInChannels.log` | `BuiltInChannels(log=True)` | off |

Set `management.health.mail.enabled: false` in Java: a mail server outage delays email; it should not mark the application down.

## Guarantees and limits

- **At least once:** a delivery can be sent twice if an instance dies mid-send; webhooks carry an `Idempotency-Key`.
- **Live push is per instance:** a notice published on one instance reaches the streams open on that instance. Nothing is lost — the others see it on their next load — and `egradx-redis` makes it live everywhere ([two instances](/docs/recipes/two-instances)).
- **Five streams per person per instance**, each reconnecting every five minutes.
- **Slack, SMS, WhatsApp and webhooks** are tested against local stand-ins of those services, not the live ones.
- **One outbox for every language:** a message queued by Java can be delivered by a Node instance, and the other way round.
