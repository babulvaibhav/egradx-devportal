## What it is

Every failure answers with the same JSON, whichever library or language produced it:

```json
{ "success": false,
  "error": { "code": "NOTE_NOT_FOUND", "message": "There is no note 42", "timestamp": "2026-10-05T12:46:17.037Z",
             "requestId": "…", "traceId": "…", "details": { } } }
```

- **`code`** is what clients switch on. The generic ones — `NOT_AUTHENTICATED`, `ACCESS_DENIED`, `NOT_FOUND`, `CONFLICT`, `INVALID_REQUEST`, `INTERNAL_ERROR` — plus the SDK's own (`AUTH_INVALID_CREDENTIALS`, `SESSION_REVOKED`…) and yours (`NOTE_NOT_FOUND`).
- **`message`** is for people, and never parsed.
- **A 5xx never reveals anything:** its message is always "Something went wrong"; the failure is logged with its stack trace and the request id.
- **`details`** appears only for codes that carry something to act on (`ORG_SELECTION_REQUIRED` lists the organizations).

| `AuthorizationException` | 403 | `ACCESS_DENIED` |
| `NotFoundException` | 404 | `NOT_FOUND` |
| `DuplicateResourceException` | 409 | `CONFLICT` |
| `NotImplementedException` | 501 | `INTERNAL_ERROR` |
| `ServerUnavailableException` | 503 | `INTERNAL_ERROR` |
| `ServerException(status)` | the status | the generic code for it |
| anything else | 500 | `INTERNAL_ERROR` |

Node and Python exceptions also take `details`. Better than a code at each throw: a class of your own extending one of these with its code fixed, as OIM's `InsufficientInventoryException` does.

## Wiring the envelope in

<Languages>
<Tab value="Java">

Nothing to write. `egradx-sdk` registers a fallback advice, `EgradxApplicationExceptionHandler`, ordered last, that answers your endpoints in the envelope: the core exceptions, Bean Validation (`@Valid`), a missing parameter, a malformed value or body, a refused `@PreAuthorize` (401 `NOT_AUTHENTICATED`, 401 `SESSION_EXPIRED` for a refused token, 403 `ACCESS_DENIED`), an unknown path or a wrong method, and anything unexpected (a logged 500). The SDK's own endpoints answer the same way.

You keep the last word:

| You want | Do |
|---|---|
| your own answer for some exceptions, the SDK's for the rest | an advice of your own handling only those; it answers first, whatever its order |
| your own envelope for everything | an advice of your own handling `Exception` **and** `AccessDeniedException` |
| the SDK's handler, changed | a bean extending `EgradxApplicationExceptionHandler`; it replaces the SDK's |
| no fallback at all | `egradx.errors.fallback.enabled: false` |

Generated projects have an advice of their own, `ApiExceptionHandler`. It is optional — the fallback answers the same without it — and is the place for your own answers; keep it, change it, or delete it:

<RepoSnippet file="apps/egradx-devportal/examples/java/backend/src/main/java/com/acme/notes/common/exception/ApiExceptionHandler.java" region="error-advice" title="backend/…/common/exception/ApiExceptionHandler.java (optional)" />

<Callout type="warn" title="A catch-all advice of your own">
  An `@ExceptionHandler(Exception.class)` in your own advice answers before the fallback, so it also catches Spring Security's `AccessDeniedException`: every refused `@PreAuthorize` becomes your 500. Handle `AccessDeniedException` too, as the advice above does, or handle only your own exceptions and leave the rest to the fallback.
</Callout>

An advice of yours extends `EgradxExceptionHandlerSupport` to answer by the same rules: override `handleBeanValidation` for your own wording; add handlers for exceptions of yours that don't extend the core ones, using `respond(status, code, message[, details])`.

The fallback comes with the next republish of `egradx-sdk` 1.0.0 ([what's new](/docs/whats-new)). Until your build has it, keep the generated advice: without one, `egradx-sdk` answers your endpoints' failures in Spring Boot's format (a `NotFoundException` becomes a 500).

</Tab>
<Tab value="Node">

`app.use(...egradxErrors())`, after every route, answers everything: the SDK's exceptions, an unreadable body, an unknown path (404), anything else (500, logged). See `src/app.ts`. Node has no validation library of its own: check bodies and throw `ValidationException`.

</Tab>
<Tab value="Python">

`sdk.install(app)` registers the handlers: the SDK's exceptions, pydantic's validation errors (400 `INVALID_REQUEST`, naming the field), unknown paths and methods, and anything else (500, logged).

</Tab>
</Languages>
