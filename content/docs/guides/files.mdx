## What it is

People attach delivery notes to orders, invoices to tickets, a photo to their profile. `egradx-file-storage` keeps those files for your application, in every language, from the same `/egradx/files/**` endpoints:

- **Files belong to an organization.** A file of another organization doesn't exist for the caller: asking for it answers 404.
- **A file can be attached to one of your records**, named by a type and an id (`order` / `42`). Who may see and add those files is your rule: you plug in an **access policy** for the type.
- **Built-in permissions** decide everything else: `egradx.file.read`, `egradx.file.write` and `egradx.file.delete`, held by every organization's Admin role. The person who uploaded a file may always read and delete it.
- **Profile photos**, one per person, readable by everyone in the organization.
- **Two backends:** a folder on local disk, the default, or any S3-compatible store (AWS S3, MinIO, Cloudflare R2, Wasabi) through the official AWS SDK.
- **Downloads** stream through your application after the check, with `Range`, `ETag` and the right `Content-Disposition`. On S3, they can redirect to a short-lived pre-signed URL instead.
- **A scanning hook** to refuse a file before it is kept (a virus scanner).

You write none of the storage: no upload endpoint, no files table, no S3 code. You add the package, choose a backend, and register a policy for each kind of record that has files.

## How it works

<Mermaid chart={`sequenceDiagram
  participant B as Browser
  participant A as Your API (with egradx-file-storage)
  participant P as Your access policy
  participant S as Disk or bucket
  B->>A: POST /egradx/files (multipart: file, attachedType=order, attachedId=42)
  A->>P: may this person WRITE to order 42?
  P-->>A: ALLOW, DENY or DEFAULT (the permissions decide)
  A->>S: stream the bytes, counting size and sha256, cut off at max-size
  A->>A: scanners, then the row and the audit record in one transaction
  A-->>B: 201 { id, name, size, contentUrl, … }
  B->>A: GET /egradx/files/{id}/content (Range: bytes=0-1023)
  A->>P: may this person READ it?
  A->>S: read that range
  A-->>B: 206, streamed`} />

1. **Upload.** `POST /egradx/files`, multipart, with the `file` part and optionally `purpose` (`attachment` by default, or a word of yours), `attachedType` and `attachedId` (both or neither). An empty file, one over `max-size`, or one whose content type isn't in `allowed-content-types` is refused first. The bytes are then streamed to the backend while their sha256 is counted.
2. **Keep or refuse.** Each scanner looks at the stored bytes, and then the row is written in the same transaction as the audit record. If anything fails, the stored bytes are deleted.
3. **List.** `GET /egradx/files?attachedType=order&attachedId=42`: the record's files the caller may read, newest first, at most 200.
4. **Download.** `GET /egradx/files/{id}/content` streams the bytes; `GET /egradx/files/{id}` gives the details.
5. **Delete.** `DELETE /egradx/files/{id}` (204) marks the row deleted, then removes the bytes. Bytes that fail to go are retried by an hourly clean-up.

The bytes are stored under `org/{organizationId}/{yyyy}/{mm}/{id}`; the row is in `egradx_file`, which the library migrates itself ([database](/docs/reference/database#file-storage)). The [HTTP reference](/docs/reference/http/files) has every request and answer.

## Backends

### Local disk

The default. `local.root` is the folder (created if missing). With several instances, it must be **one folder they all share**, such as a network volume; in a container, a volume, or the files go with the container.

### S3 and S3-compatible stores

`backend: s3` stores the bytes in a bucket, which must exist. The S3 client is optional, so local disk needs nothing more:

| Java | Node | Python |
|---|---|---|
| add `software.amazon.awssdk:s3` (and the AWS BOM, or a version) | `npm install @aws-sdk/client-s3 @aws-sdk/s3-request-presigner` | `pip install "egradx-file-storage[s3]"` (aioboto3) |

| Cloudflare R2 | `https://<account id>.r2.cloudflarestorage.com` | `auto` | `true` |
| Wasabi | `https://s3.<region>.wasabisys.com` | the bucket's region | `true` |

## Who may do what

| | Reading (details, bytes, list) | Uploading | Deleting |
|---|---|---|---|
| A file not attached to a record | `egradx.file.read` | `egradx.file.write` | `egradx.file.delete` |
| A file attached to a record with a policy | the policy, `READ` | the policy, `WRITE` | the policy, `DELETE` |
| The file's uploader | always | — | always |
| A profile photo | everyone in the organization | its owner, through `/my/profile/photo` | its owner |
| Another organization's file | 404 | — | 404 |

- **Inside the caller's organization, a refusal answers 403** `ACCESS_DENIED`, for reading and deleting alike, and a refused download is recorded (`files.file.download_denied`).
- **Listing** without leave to read the record's files still shows the files the caller uploaded to it.
- The three permissions are on every organization's Admin role. Give them to other roles as you would [your own](/docs/guides/authorization), or let a policy decide for your records.

### The access check for your records

A policy answers for one `attachedType`. It sees who is asking (user, organization, authorities), what they want to do (`READ`, `WRITE` or `DELETE`), the record's id, and the file's id (none when uploading or listing). It answers:

- **`ALLOW`** or **`DENY`**: settled.
- **`DEFAULT`**: the built-in permission decides, as if there were no policy.

Check that the record exists **in the caller's organization**. The id comes from the client; without that check, someone could attach files to another organization's record id.

<Languages>
<Tab value="Java">

A bean per type:

```java title="order/infrastructure/OrderFileAccess.java"
@Component
public class OrderFileAccess implements EgradxFileAccessPolicy {

    private final OrderRepository orders;

    public OrderFileAccess(OrderRepository orders) {
        this.orders = orders;
    }

    @Override
    public String attachedType() {
        return "order";
    }

    @Override
    public Decision decide(Request request) {
        UUID orderId;
        try {
            orderId = UUID.fromString(request.attachedId());
        } catch (IllegalArgumentException notAnId) {
            return Decision.DENY;
        }
        if (orders.findByIdAndOrganizationId(orderId, request.organizationId()).isEmpty()) {
            return Decision.DENY;                                    // not an order of this organization
        }
        String needed = request.action() == Action.READ ? "order.read" : "order.create";
        return request.authorities().contains(needed) ? Decision.ALLOW : Decision.DENY;
    }
}
```

import { fileAccessPolicy } from '@babulvaibhav/egradx-file-storage';

export const orderFiles = (prisma: PrismaClient) =>
  fileAccessPolicy('order', async (request) => {
    if (!isUuid(request.attachedId)) return 'DENY';
    const order = await prisma.order.findFirst({ where: { id: request.attachedId, organizationId: request.organizationId }, select: { id: true } });
    if (!order) return 'DENY';                                     // not an order of this organization
    const needed = request.action === 'READ' ? 'order.read' : 'order.create';
    return request.authorities.has(needed) ? 'ALLOW' : 'DENY';
  });

from sqlalchemy import text

from egradx.core import is_uuid
from egradx.files import EgradxFileAccessPolicy, FileAccessRequest, FileAction, FileDecision


def order_files(engine) -> EgradxFileAccessPolicy:
    async def decide(request: FileAccessRequest) -> FileDecision:
        if not is_uuid(request.attached_id):
            return FileDecision.DENY
        async with engine.connect() as connection:
            found = (await connection.execute(
                text("SELECT 1 FROM orders WHERE id = CAST(:id AS uuid) AND organization_id = CAST(:org AS uuid)"),
                {"id": request.attached_id, "org": request.organization_id})).first()
        if found is None:
            return FileDecision.DENY                                   # not an order of this organization
        needed = "order.read" if request.action == FileAction.READ else "order.create"
        return FileDecision.ALLOW if needed in request.authorities else FileDecision.DENY

    return EgradxFileAccessPolicy("order", decide)

# FilesOptions(..., policies=[order_files(engine)])

## Scanning uploads

A scanner sees each upload **after the bytes are stored and before the row is committed**. It returns a reason to refuse the file, or nothing to keep it. A refusal deletes the bytes and answers `FILE_REJECTED` (422). There is none by default.

## Downloads

`GET /egradx/files/{id}/content` answers:

- **The bytes, streamed**, with `Content-Type`, `Content-Length`, `ETag` (the sha256) and `X-Content-Type-Options: nosniff`.
- **`Content-Disposition`**: `inline` for images (but not SVG, which can carry script) and PDF, so the browser shows them; `attachment` for everything else, so it saves them. The name is RFC 5987-encoded.
- **`Range`**: one range answers **206** with `Content-Range`; several ranges answer 200 with everything; a range past the end answers 416.
- **Pre-signed redirect** (S3 only, `s3.presigned-downloads: true`): after the same check, **302** to a URL on the bucket that works for `s3.presigned-ttl` (5 minutes), with the same disposition. The bytes then don't pass through your application. `<img>` and links follow it as they are; a script's `fetch()` needs [CORS on the bucket](/docs/operate/troubleshooting#a-download-fails-from-a-script-with-pre-signed-downloads-on).

A download is a plain `GET` that needs the session. A `<img src>` sends no bearer token, so with tokens in the browser use the client's `displayUrl` or `useFileObjectUrl`, which download into a `blob:` URL. Behind the Next.js backend-for-frontend the cookie goes with the plain URL. See [the frontend](#the-frontend).

## Profile photos

- **`PUT /egradx/auth/my/profile/photo`** (multipart `file`) stores the photo, deletes the previous one, and answers with the profile, whose `photoUrl` is now `/egradx/files/{id}/content`. PNG, JPEG or WebP, at most 5 MB by default (`profile-photo.*`).
- **`DELETE /egradx/auth/my/profile/photo`** (204) deletes it and clears `photoUrl`.
- **One per person.** Setting a photo while in another organization replaces it there too.
- **Readable by everyone in the organization it was uploaded in.** In another organization it answers 404, so a person in several organizations shows their initials in the others until they set it again there.
- `photoUrl` in `PUT /egradx/auth/my/profile` accepts an `http(s)` URL or a stored photo's `/egradx/files/{id}/content`, nothing else.

These endpoints are served by `egradx-file-storage`, not by sign-in: without the package, `photoUrl` is an `http(s)` URL only. See [let people set a profile photo](/docs/recipes/set-a-profile-photo).

- **Uploads report progress** through XMLHttpRequest, the one browser API that does; without `onProgress` they go through the client's fetch. Every upload and download gets the token, the refresh and the retry every call gets.
- **`checkFile`, `accept` and `maxSize`** refuse a file before it is sent, with the same codes the server uses, so one wording covers both. Keep them in step with the server's `max-size`, `allowed-content-types` and `profile-photo.*`: they only save sending a file the server would refuse.
- **Showing a file with tokens in the browser** (Vite): `displayUrl` and `useFileObjectUrl` download into a `blob:` URL and revoke it when done. A Content-Security-Policy must allow `blob:` in `img-src` (and `frame-src` for PDFs).
- **With Next.js**, the backend-for-frontend passes multipart bodies on byte for byte and streams downloads back with their headers, `Range` included. The cookie goes with a plain URL, so `<img src="/bff/egradx/files/{id}/content">` works and `displayUrl` returns it without downloading. **Keep the BFF's path out of `proxy.ts`'s matcher**: a request the proxy matches has its body cut at `experimental.proxyClientMaxBodySize` (10 MB by default), so a larger upload reaches the API broken. The BFF holds an upload in memory while it passes, so it can resend it after a refresh.
- **The copy-in screens** word every refusal in `components/egradx/files/file-format.ts` (`fileErrorText`).

## Audit and observations

| Audit action | Recorded when |
|---|---|
| `files.file.uploaded` | a file is kept, with its name, size, type, purpose and record |
| `files.file.deleted` | a file is deleted, by someone or by replacing a profile photo |
| `files.file.download_denied` | a read is refused in the caller's organization. Successful reads are not recorded |

The upload's audit record is written in the row's transaction. Uploads and downloads are observed as `egradx.files.upload` and `egradx.files.download` (traces and metrics, [observability](/docs/guides/observability)).

## Guarantees and limits

- **No row without bytes, no bytes left without a row.** The bytes are stored first; a failure in the scanners, the row or the audit record deletes them. A delete marks the row first, so the file is gone at once; bytes that fail to delete are removed by the hourly clean-up.
- **Organization-scoped**: a file is never visible outside its organization, whatever the policy says.
- **Sizes are enforced while streaming**, not after: an oversized upload is cut off at the limit.
- **The same table, keys and endpoints in every language**: Java, Node and Python services can share one database and one bucket.
- **One request per upload.** There is no resumable or chunked upload yet: a large file on a bad connection starts again. That is the next step, on the same files API.
- **Profile photos are one per person** and readable only within the organization they were uploaded in.
- **No image processing**: photos are kept as uploaded (no resizing or thumbnails), and the browser scales them.
- **Downloads go through your application** unless pre-signed downloads are on, which needs S3.
- **Local disk with several instances** needs one shared folder; otherwise each instance sees only what it stored.

## In OIM

All three OIM backends store files on local disk, in the `oim_files` volume of `docker-compose.yml` (`EGRADX_FILES_BACKEND=s3` and the `EGRADX_FILES_S3_*` variables switch to a bucket). Orders have attachments, decided by `OrderFileAccess`: whoever may see the order sees its files; whoever may create orders adds and deletes them.

The Vite frontend shows an order's files with `OrderAttachments` (on `useAttachments` and `useFileUpload`), the photo on the account page with `ProfilePhotoCard`, and the photo in the header with `UserAvatar` (both on `useProfilePhoto`). Its nginx allows bodies of 30 MB (`client_max_body_size 30m`) for the 25 MB limit, and its Content-Security-Policy allows `blob:` in `img-src`. The Next.js frontend uses the copy-in `attachments` and `avatar-upload` screens.
