## What it is

An append-only record of what people did: sign-ins and refusals, role changes, settings — the SDK records those itself — and the business changes **your** application records. Each record says who did it (from the signed-in caller), in which organization, to what (an entity), with the state before and after, and the request and trace it came from.

- **With the transaction:** a record of a change commits with the change, or not at all. A record never describes a change that rolled back, and a change never commits without its record.
- **Failures survive:** a refused or failed attempt (`denied(...)`, `failure(...)`) is written on its own and stays even when the work rolls back.
- **Append-only:** the database refuses to change or delete records, except the retention purge.
- **Secrets never stored:** keys like `password`, `token`, `secret`, `otp` are redacted wherever they appear in a state.

## Reading it

| Endpoint | What it gives | Needs |
|---|---|---|
| `GET /egradx/audit/events` | the caller's organization's records, newest first, a page at a time (`cursor`, `size` ≤ 200) | `egradx.audit.read` |
| `GET /egradx/audit/events/{id}` | one record | same |
| `GET /egradx/audit/timeline?entityType=&entityId=` | one thing's history | same |
| `GET /egradx/audit/actions` | the catalog | same |
| `GET /egradx/audit/events/export` | the same filters as CSV (up to 100 000 rows; recorded itself) | same |
| `/egradx/audit/platform/**` | the same across every organization | `egradx.audit.platform.read` |

Filters: `from`, `to`, `action`, `actionPrefix`, `category`, `outcome`, `actorId`, `actorType`, `entityType`, `entityId`, `changedField`, `correlationId` (a request or trace id) and `q` (text). Repeat a parameter for "any of". The [web packages](/docs/guides/web) have hooks for all of it, and a ready audit screen (`audit-log`).

## A library of your own

A library that must not depend on the audit package publishes the same event and lets the application record it: Java `ApplicationEventPublisher.publishEvent(EgradxAuditEvent)`, Node `publishAuditEvent(event)`, Python `await publish_audit_event(event)` — each from the core package.

## Configuration

| | Java (`egradx.audit.*`) | Node (`audit: {…}`) | Python (`audit={…}`) | Default |
|---|---|---|---|---|
| Keep records for | `retention.default-period: 7y` | `retention: { defaultPeriod: '7y' }` | `"retention": AuditRetentionSettings(default_period="7y")` | for ever |
| …per category | `retention.categories.auth: 2y` | `retention: { categories: { auth: '2y' } }` | `categories={"auth": "2y"}` | — |
| Purge every | `retention.purge-interval: 1h` | `intervalMs` | `interval_seconds` | 1 hour |
| Only some instances purge | `retention.enabled: false` on the others | `enabled: false` | `enabled=False` | all, one at a time |
| More secret keys | `redaction.keys`, `.fragments` | `redaction: { keys, fragments }` | `redaction_keys`, `redaction_fragments` | built-in list |
| Largest state kept | `max-state-bytes: 32768` | `maxStateBytes` | `max_state_bytes` | 32 KB, then a marker |
| Largest export | `export.max-rows: 100000` | `export: { maxRows }` | `export_max_rows` | 100 000 |

Node and Python accept single-unit periods only (`7y`, `18m`, `90d`); a wrong one is reported when the purge runs. Java also takes combined ones (`1y6m`) and refuses a wrong one at start-up.

## Guarantees and limits

- **One trail for every language:** the same table and formats, so Java, Node and Python services can share a database and read each other's records.
- **Append-only against your application**, not against the database's owner: there is no tamper-evident chain.
- **Personal data:** records cannot be edited, so retention is how they leave. Keep states to what an auditor needs, and add your own sensitive keys to the redaction list.
- **Throttled repeats:** a burst of identical refusals (a password guessed many times) is kept once per minute.
- **PostgreSQL only.**
