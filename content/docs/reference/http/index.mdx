An application on the SDK serves these endpoints itself, under its own base path (OIM's is `/api`, so its sign-in is `/api/egradx/auth/login`). Java, Node and Python serve the same paths, take the same bodies and answer the same JSON — the conformance suite checks it — so a frontend works with any of them.

<Cards>
  <Card title="Sign-in & identity" href="/docs/reference/http/auth">`/egradx/auth/**`: sign-in, sessions, accounts, organizations, users, roles, invitations, profiles.</Card>
  <Card title="Audit trail" href="/docs/reference/http/audit">`/egradx/audit/**`: records, history, export, the action catalog.</Card>
  <Card title="Notifications" href="/docs/reference/http/notification">`/egradx/notifications/**`: the inbox, its stream, preferences, and administration.</Card>
</Cards>

## For every endpoint

- **Signed in** with `Authorization: Bearer <access token>`; sign-in, renewal, the forgotten-password flow and invitation links are open. See [headers and tokens](/docs/reference/headers-and-tokens).
- **Refusals** are the [error envelope](/docs/reference/errors): 401 `NOT_AUTHENTICATED` or `SESSION_EXPIRED`, 403 `ACCESS_DENIED`, 404 for anything outside the caller's organization.
- **Request ids:** send `X-Request-ID`; every answer carries one.
- **Lists** page with `page` and `size` (sign-in and notifications) or with an opaque `cursor` (the audit trail).

The contracts behind these pages are `contracts/openapi/auth.yaml`, `audit.yaml` and `notification.yaml` in the SDK's repository; the [browser client](/docs/guides/web) has typed calls generated from them.
